# Decisions: TelegramCustom

В этом документе зафиксированы ключевые архитектурные и технические решения, принятые в ходе разработки TelegramCustom. Они защищают проект от регрессий и объясняют «почему сделано именно так».

---

## Decision 1: Загрузка сообщений через прямой MTProto `MTPmessages_GetHistory` + `history->addOlderSlice`

- **Почему:** Стандартный вызов `session->api().requestHistory(...)` в коде tdesktop лишь помечает диапазон в разреженном индексе истории, но не наполняет блоки `history->blocks` объектами `HistoryItem`. Из-за этого при открытии ранее не посещенных в основном клиенте чатов оверлей видел пустую историю сообщений.
- **Когда/в каком контексте:** Обнаружено при тестировании оверлея на чате «Марат» (скриншот `uploaded_media_1_1787846899901.png`), где отображалась только 1 последняя реплика.
- **Какие альтернативы рассматривались:**
  1. Использовать `session->api().requestHistory(...)` с ожиданием таймером (не работает, блоки в памяти не создаются).
  2. Ждать, пока пользователь откроет чат в основном окне Telegram (неприемлемо для автономного игрового оверлея).
  3. Прямой запрос MTProto `MTPmessages_GetHistory` с передачей ответа в `history->addOlderSlice(*histList)`.
- **Почему выбрали этот вариант:** `history->addOlderSlice` — нативный метод tdesktop, который парсит список пользователей и чатов, создает экземпляры `HistoryItem` и корректно складывает их в `history->blocks`, откуда оверлей строит UI переписки.
- **Что зависит от этого решения:** Полная автономность оверлея от основного окна Telegram.
- **Можно ли менять:** Только если найдена более высокоуровневая обертка в API tdesktop, гарантированно создающая блоки `HistoryItem`.

## Decision 2: Обертка облачков сообщений в контейнер `rowWidget` (`QHBoxLayout` + `addStretch`)

- **Почему:** В стандартном вертикальном лейауте Qt (`QVBoxLayout::addWidget(bubble, 0, Qt::AlignLeft)`) динамический расчет высоты по ширине (`heightForWidth`) для `QLabel` с `wordWrap(true)` работает некорректно. Длинные фразы срезались до одной строки.
- **Когда/в каком контексте:** Запрос пользователя со скриншотом `uploaded_media_1787837259210.png` (сообщения «Да пока можно без...» и «А и ещё я тебе там...» обрезались).
- **Какие альтернативы рассматривались:**
  1. Захардкодить фиксированную высоту или считать высоту через `QFontMetrics` вручную (хрупко при разных шрифтах и переводах строк).
  2. Обернуть пузырь в контейнер строки во всю ширину с `QHBoxLayout`, где для входящих сообщений стретч ставится справа, а для исходящих — слева.
- **Почему выбрали этот вариант:** Вариант со строковым контейнером заставляет Qt честно рассчитывать ширину пузыря (с ограничением `maximumWidth(460)`) и динамически расширять строку по высоте под любое количество строк текста.
- **Что зависит от этого решения:** Корректность отображения всех текстовых сообщений в оверлее.
- **Можно ли менять:** **НЕЛЬЗЯ ЛОМАТЬ.** Возврат к прямому добавлению `bubble` в `_messagesLayout` гарантированно вернет баг обрезания текста.

## Decision 3: Обязательный вызов `goodThumbnailWanted()` перед `goodThumbnail()`

- **Почему:** В tdesktop в классе `DocumentMedia` есть строгий ассерт: `Assert((_flags & Flag::GoodThumbnailWanted) != 0)`. Попытка прочитать миниатюру без предварительного вызова флага приводит к мгновенному крашу приложения.
- **Когда/в каком контексте:** Коммит `603ee99` вызвал краш клиента при открытии чата с гифками. Исправлено в коммите `4c9fc66`.
- **Какие альтернативы рассматривались:** Читать только сырые байты файла (слишком медленно и тяжело для памяти).
- **Почему выбрали этот вариант:** Это стандартный контракт работы с медиа-кэшем tdesktop.
- **Что зависит от этого решения:** Стабильность работы приложения без крашей.
- **Можно ли менять:** **КАТЕГОРИЧЕСКИ НЕЛЬЗЯ УДАЛЯТЬ `goodThumbnailWanted()`.**

---

## Decision 4: Прямая стилизация `verticalScrollBar()->setStyleSheet(...)`

- **Почему:** Глобальный селектор `QScrollArea { ... }` или `QScrollBar:vertical` в стилях контейнера часто игнорируется на Windows из-за вмешательства нативных стилей Windows Vista/10/11, что приводило к появлению широкого белого скроллбара.
- **Когда/в каком контексте:** Жалоба пользователя на некрасивый белый скроллбар в оверлее.
- **Какие альтернативы рассматривались:** Написание кастомного `QStyle` (избыточно сложно).
- **Почему выбрали этот вариант:** Прямое назначение CSS на экземпляр скроллбара жестко переопределяет нативный отрисовщик Windows.
- **Что зависит от этого решения:** Эстетичный ультратёмный вид оверлея.
- **Можно ли менять:** Нет, это наиболее надежный способ стилизации скроллбаров в Qt.

---

## Decision 5: Архитектура «Overlay Patch» в GitHub Actions вместо форка 50GB репозитория

- **Почему:** Полная кодовая база tdesktop вместе со всеми субмодулями и библиотеками весит гигантский объем. Хранить её целиком в git-репозитории проекта нерационально.
- **Когда/в каком контексте:** Проектирование CI/CD пайплайна в `.github/workflows/build_custom_win.yml`.
- **Какие альтернативы рассматривались:** Хранить полный монолитный форк со всеми сабмодулями прямо в репозитории.
- **Почему выбрали этот вариант:** Наш репозиторий содержит только кастомные файлы (`custom_features/`, `settings_custom.*`, и измененные upstream-файлы). В CI/CD клонируется официальный тег `v7.0.9`, наши файлы копируются поверх, и происходит чистая сборка.
- **Что зависит от этого решения:** Скорость клонирования репозитория, чистота истории git.
- **Можно ли менять:** Менять нельзя, вся автоматика завязана на этот процесс.
